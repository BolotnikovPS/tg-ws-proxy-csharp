# Требования к реализации взаимодействия TBotPlatform с Bot API

> Назначение: контракт, которому **должна удовлетворять клиентская реализация
> TBotPlatform** для корректной работы с локальным Bot API-сервером
> `tg-ws-proxy`. Документ описывает поведение клиента («клиент должен …»),
> а не внутреннее устройство сервера. Серверный контракт (URL, форматы, ошибки)
> зафиксирован в [bot-api.md](bot-api.md); здесь он переведён в проверяемые
> требования к клиенту.

Каждое требование имеет идентификатор `REQ-…`, формулировку и проверяемый
критерий приёмки. Приоритеты: **M** — обязательное (без него интеграция не
работает или небезопасна), **S** — желательное, **O** — опциональное.

---

## 1. Транспорт и адресация

### REQ-01 (M) Базовый адрес задаётся, а не зашивается
Клиент должен принимать адрес локального Bot API-сервера как параметр
конфигурации (например `http://proxy-host:80`) и строить запросы относительно
него. Адрес `api.telegram.org` не используется.

**Приёмка:** при изменении адреса сервера код клиента не меняется.

### REQ-02 (M) Маршруты вызова
Клиент должен вызывать методы по схеме `/{token}/{method}` и `/{file_path}` для
файлов, то есть:

```
GET  /bot{token}/{method}
POST /bot{token}/{method}
GET  /file/bot{token}/{file_path}
POST /file/bot{token}/{file_path}
```

`{token}` — полный токен бота (`<botId>:<secret>`), `{method}` — имя метода,
`{file_path}` — маркер, ранее полученный из `getFile`.

**Приёмка:** любой поддерживаемый метод вызывается по одному из этих шаблонов.

### REQ-03 (M) Поддержка GET и POST
Клиент должен уметь отправлять аргументы двумя способами:
- `GET` — аргументы в query-строке (значения как строки);
- `POST` — аргументы в JSON-теле или `multipart/form-data` (для медиа-методов).

**Приёмка:** метод без файлов работает через GET и POST+JSON; медиа-метод — через
POST+multipart.

---

## 2. Аргументы методов

### REQ-04 (M) Именование аргументов — официальный формат Bot API
Клиент должен передавать аргументы с именами и типами официального Bot API
(`chat_id`, `text`, `message_id`, `file_id`, `caption`, `parse_mode`,
`reply_markup`, `disable_notification`, `reply_to_message_id` и т.д.). Числа
передаются как JSON-числа (в GET — строками), булевы — как `true`/`false`.

**Приёмка:** сервер принимает запрос без ошибки `400` по причине имени/типа.

### REQ-05 (M) Обязательные аргументы заполняются всегда
Клиент должен гарантировать наличие минимального набора аргументов для каждого
метода (иначе сервер вернёт `400 "<param> is required for <method>"`):

| Метод | Обязательные аргументы |
|---|---|
| `sendMessage` | `chat_id`, `text` |
| `sendPhoto`/`sendDocument`/`sendAudio`/`sendVideo`/`sendAnimation`/`sendVoice`/`sendVideoNote`/`sendSticker` | `chat_id`, соответствующий медиа-аргумент (`photo`/`document`/…) |
| `sendMediaGroup` | `chat_id`, `media` (массив) |
| `getFile` | `file_id` |
| `editMessageText` | `text`; и `chat_id`+`message_id`, либо `inline_message_id` |
| `editMessageCaption` | `chat_id`+`message_id`, либо `inline_message_id` |
| `editMessageMedia` | `media`; `chat_id`+`message_id`, либо `inline_message_id` |
| `deleteMessage` | `chat_id`, `message_id` |
| `forwardMessage` | `chat_id`, `from_chat_id`, `message_id` |
| `copyMessage` | `chat_id`, `from_chat_id`, `message_id` |
| `answerCallbackQuery` | `callback_query_id` |
| `getChat`/`getChatAdministrators`/`getChatMemberCount`/`setChatTitle`/`setChatDescription`/`setChatPhoto`/`leaveChat` | `chat_id` |
| `getChatMember` | `chat_id`, `user_id` |
| `banChatMember` | `chat_id`, `user_id` |
| `sendChatAction` | `chat_id`, `action` |
| `answerInlineQuery` | `inline_query_id`, `results` |

**Приёмка:** клиент не отправляет запрос с отсутствующим обязательным аргументом;
ошибки `400` от сервера по этой причине не возникают.

### REQ-06 (M) Медиа передаётся как file_id либо как файл
Для медиа-методов клиент должен передавать в медиа-аргументе (`photo`,
`document`, …) **либо** строку `file_id` (повторное использование уже
загруженного файла), **либо** файл через `multipart/form-data`. Для
`sendMediaGroup` ссылки на файлы внутри массива `media` оформляются как
`attach://<имя>` и передаются отдельными файловыми частями.

**Приёмка:** новая загрузка и повторное использование file_id дают корректный
ответ без `400`.

## 3. Авторизация и заголовки

### REQ-07 (M) Первый логин требует api_id/api_hash
Клиент должен при первом входе бота (создание auth_key) передавать заголовки:
- `X-Telegram-Api-Id` — числовой `api_id` (с my.telegram.org);
- `X-Telegram-Api-Hash` — `api_hash`.

После сохранения сессии сервером заголовки не обязательны, но клиент должен
допускать их передачу на каждом запросе (безвредно).

**Приёмка:** без заголовков при первой авторизации сервер вернёт `401`; клиент
корректно обрабатывает этот код как «требуется логин с api_id/api_hash».

### REQ-08 (M) Обработка 401 как «нужен логин»
Клиент должен отличать `error_code=401` (требуется логин) от прочих ошибок и
реагировать повторной отправкой с заголовками `X-Telegram-Api-Id` /
`X-Telegram-Api-Hash`, а не трактовать как фатальную ошибку.

**Приёмка:** сценарий первого логина проходит без ручного вмешательства.

---

## 4. Разбор ответов

### REQ-09 (M) Единая обёртка {ok, result}
Клиент должен разбирать ответ строго по обёртке:
- успех — `{ "ok": true, "result": <…> }`;
- ошибка — `{ "ok": false, "error_code": <int>, "description": "<текст>" }`.

**Приёмка:** клиент извлекает `result` только при `ok=true`, иначе читает
`error_code`/`description`.

### REQ-10 (M) Типы результата
Клиент должен уметь десериализовать `result` как типы официального Bot API:
`User`, `Message`, `Message[]`, `Chat`, `ChatMember`, `File`, `true` (для
bool-методов) и т.д. Для bool-методов `result` равен `true`.

**Приёмка:** все поддерживаемые методы дают корректно типизированный `result`.

### REQ-11 (M) Не-200 статус при ошибке не ломает разбор
Клиент должен допускать ответы с HTTP-статусом, отличным от 200, для ошибок
`413` и `429` и **при этом разбирать тело** как валидный `{ok:false, …}`.

**Приёмка:** при `413`/`429` клиент читает `error_code`/`description` из тела,
а не только из HTTP-статуса.

---

## 5. Поддерживаемые методы и ограничения

### REQ-12 (M) Работа в рамках перечня методов
Клиент должен использовать только поддерживаемые методы и не полагаться на
прозрачную пересылку. Поддерживаются:

**Ядро:** `getMe`, `getUpdates`, `sendMessage`.
**Медиа и файлы:** `sendPhoto`, `sendDocument`, `sendAudio`, `sendVideo`,
`sendAnimation`, `sendVoice`, `sendVideoNote`, `sendSticker`, `sendMediaGroup`,
`getFile`.
**Правка/пересылка:** `editMessageText`, `editMessageCaption`, `editMessageMedia`,
`deleteMessage`, `forwardMessage`, `copyMessage`, `answerCallbackQuery`.
**Чаты:** `getChat`, `getChatAdministrators`, `getChatMember`,
`getChatMemberCount`, `setChatTitle`, `setChatDescription`, `setChatPhoto`,
`leaveChat`, `banChatMember`.
**Служебные:** `sendChatAction`, `setMyCommands`, `getMyCommands`,
`answerInlineQuery`.

**Приёмка:** клиент не вызывает методы вне этого списка без обработки `501`.

### REQ-13 (M) Обработка 501 «метод не реализован»
Клиент должен корректно обрабатывать `error_code=501` с описанием
`method '...' is not implemented` как «метод не поддерживается сервером», и не
повторять такой запрос бесконечно.

**Приёмка:** неподдерживаемый метод не приводит к зависанию/зацикливанию клиента.

### REQ-14 (M) Режим long-polling (getUpdates), без webhook
Клиент должен работать в режиме long-polling через `getUpdates` (параметры
`offset`/`limit`/`timeout`) и **не** полагаться на webhook: сервер их не
поддерживает.

**Приёмка:** обновления стабильно доставляются через `getUpdates`; webhook-путь не
используется.

---

## 6. Скачивание файлов

### REQ-15 (M) Двухшаговая загрузка файла
Клиент должен скачивать файл в два шага:
1. `getFile` с `file_id` → получить объект `File` с полем `file_path`;
2. `GET /file/bot{token}/{file_path}` → получить байты.

**Приёмка:** содержимое файла получается по `file_path`, а не напрямую из
`getFile`.

### REQ-16 (M) file_path не модифицируется
Клиент должен использовать `file_path` как непрозрачный маркер **без
изменения/декодирования** и вставлять его в URL скачивания как есть.

**Приёмка:** скачивание проходит с оригинальным `file_path`.

### REQ-17 (M) Обработка ограничений скачивания
Клиент должен обрабатывать при скачивании:
- `413` — файл не помещается в кэш сервера (`botApi.maxFileCacheBytes`);
- `502` с `CDN file download is not supported yet` — CDN-файл пока недоступен;
- `404` — `file_path` не найден (кэш вытеснен или истёк).

**Приёмка:** клиент не падает на этих кодах и сообщает пользователю понятную
причину.

---

## 7. Лимиты и отказоустойчивость

### REQ-18 (M) Соблюдение per-bot rate-limit
Клиент должен укладываться в `botApi.requestsPerSecondPerToken` (по умолчанию
`30` запросов/сек на бота) и обрабатывать `error_code=429`
(`Too Many Requests: rate limit exceeded`) отступлением (backoff) и повтором
позже.

**Приёмка:** при превышении лимита клиент не ретраит мгновенно; после паузы
запрос проходит.

### REQ-19 (M) Лимит размера загрузки
Клиент должен учитывать `botApi.maxUploadBytes` (по умолчанию 20 MiB) и не
отправлять multipart суммарно больше лимита; при `413` — сообщать об ошибке,
а не бесконечно повторять.

**Приёмка:** загрузка сверх лимита завершается штатной ошибкой, не зависает.

### REQ-20 (S) Обработка транспортных ошибок 502
Клиент должен отличать `502` (`Bot transport error` / `Internal bot gateway
error`) от ошибок метода и применять ограниченный повтор, т.к. сервер может
переподключаться к Telegram.

**Приёмка:** временный `502` не роняет сессию клиента.

---

## 8. Безопасность и метаданные

### REQ-21 (M) Токен передаётся без раскрытия в логах
Клиент должен передавать токен в пути URL (`/bot{token}/…`) и при этом не
логировать его в открытом виде (маскировать `botId:***` или аналогично).

**Приёмка:** в логах клиента нет полного токена.

### REQ-22 (S) Учёт маскировки секретов сервером
Клиент должен понимать, что сервер маскирует секреты в логах (формат
`12345:***`), и не ожидать полного `api_hash`/токена в каких-либо ответах или
диагностике.

**Приёмка:** клиент не пытается восстановить секрет из ответов сервера.

---

## 9. Совместимость со стандартным Bot API

### REQ-23 (M) Совместимость формата без переписывания клиента
Клиент должен подключаться к серверу через стандартную точку входа Bot API
(например `TelegramBotClientOptions("http://proxy-host:80")`) без изменения
бизнес-логики бота; расхождение с `api.telegram.org` ограничено только адресом
и расширением с заголовками `X-Telegram-Api-Id`/`X-Telegram-Api-Hash`.

**Приёмка:** существующий бот TBotPlatform работает с сервером, поменяв только
базовый адрес.
