# Требования к реализации интеграции Telegram.Bot с Bot API-шлюзом

> Назначение: контракт, которому **должна удовлетворять клиентская реализация на
> пакете `Telegram.Bot`** (`github.com/TelegramBots/telegram.bot`) для корректной
> работы с локальным Bot API-шлюзом сервиса `tg-ws-proxy-csharp`. Документ
> описывает поведение клиента («клиент должен …»), а не внутреннее устройство
> сервера. Серверный контракт (URL, форматы, ошибки, лимиты) зафиксирован в
> [bot-api.md](../bot-api.md); здесь он переведён в проверяемые требования к
> интеграции на Telegram.Bot. Факты о пакете (версия, API, транспорт) проверены
> по репозиторию `TelegramBots/telegram.bot` на tag `v22.10.4` и по официальной
> документации («Telegram Bots Book»).
>
> Дата составления: 2026-11-22. Целевая версия пакета: **Telegram.Bot 22.10.4**
> (покрывает Bot API 10.4). Сверка шлюза с апстримом обновлена до **Bot API 10.5**
> (22.11.2026, см. [bot-api.md](../bot-api.md)); `getMe` в шлюзе уже возвращает
> `BotFullInfo` (10.5), `setMySettings` остаётся `501` — см.
> [PLAN-BOT-API-10.5.md](PLAN-BOT-API-10.5.md). Для 10.5-контента (`BotFullInfo`,
> `setMySettings`) клиенту нужен пакет новее 22.10.4.

Каждое требование имеет идентификатор `REQ-TB-…`, формулировку и проверяемый
критерий приёмки. Приоритеты: **M** — обязательное (без него интеграция не
работает или небезопасна), **S** — желательное, **O** — опциональное.

> Префикс `TB` в ID отличает требования этого контракта от `REQ-…` документа
> [REQUIREMENTS-BOT-API.md](REQUIREMENTS-BOT-API.md) (интеграция TBotPlatform).

## 1. Общая совместимость

### REQ-TB-01 (M) Бот на Telegram.Bot работает со шлюзом сменой адреса и заголовков
Существующий бот, написанный на `Telegram.Bot`, должен подключаться к шлюзу без
изменения бизнес-логики: расхождение с `api.telegram.org` ограничивается
(1) базовым адресом (`TelegramBotClientOptions(token, baseUrl)`) и
(2) добавлением заголовков `X-Telegram-Api-Id` / `X-Telegram-Api-Hash`.
Все стандартные вызовы (методы, файлы, long polling) продолжают работать как с
официальным Bot API-сервером.

**Приёмка:** смена `baseUrl` и добавление двух заголовков — единственные изменения
конфигурации; бот на Telegram.Bot полноценно работает со шлюзом.

### REQ-TB-02 (M) Версия пакета покрывает апстрим шлюза
Клиент должен использовать версию `Telegram.Bot`, покрывающую Bot API не ниже
версии, требуемой используемыми методами шлюза. На момент составления достаточно
**22.10.4** (покрывает Bot API 10.4, и новее в той же мажорной линии): `getMe` шлюза
уже возвращает `BotFullInfo` (10.5), а `setMySettings` отвечает `501`
(сверка шлюза — Bot API 10.5, см. [bot-api.md](../bot-api.md)). Для типизированной
работы с 10.5-контентом (`BotFullInfo`, `setMySettings`) клиенту нужен пакет новее
22.10.4. Старые версии (≤19.x, `MakeRequestAsync`/`UpdateReceiver`) непригодны:
их API несовместим с описанной ниже настройкой.

**Приёмка:** в проекте используется `Telegram.Bot` ≥ 22.10.4; код компилируется
против API v22 (`TelegramBotClientOptions`, `StartReceiving`/`ReceiveAsync`).

## 2. Настройка клиента: адрес, токен, HttpClient, таймаут

### REQ-TB-03 (M) Базовый адрес задаётся параметром
Клиент должен создавать клиент через
`new TelegramBotClientOptions(token, baseUrl)` (или эквивалент), где `baseUrl` —
адрес шлюза вида `scheme://host[:port]` (например `http://localhost:80`).
`api.telegram.org` не используется.

Особенность пакета: `ExtractBaseUrl` **отбрасывает path/query/fragment** и требует
абсолютный URI со scheme и authority; некорректный адрес → `ArgumentException`.
Поэтому адрес шлюза должен быть голым authority — префикс-путь (`http://host:8081/v1`)
не поддерживается, и клиент не должен «тихо» работать с путём, рассчитывая, что он
попадёт в URL.

**Приёмка:** при `baseUrl = "http://localhost:8081"` и токене `1234:asdfg`
`BaseRequestUrl == "http://localhost:8081/bot1234:asdfg"`,
`BaseFileUrl == "http://localhost:8081/file/bot1234:asdfg"`; путь в `baseUrl`
не используется (валидация пакета, `ArgumentException` при неверном адресе).

### REQ-TB-04 (M) `useTestEnvironment` не используется
Клиент не должен включать тестовое окружение. При `useTestEnvironment: true` пакет
добавляет суффикс `/test` в URL (`{base}/bot{token}/test`), которого шлюз не
поддерживает.

**Приёмка:** все запросы идут строго на `{base}/bot{token}/{method}` и
`{base}/file/bot{token}/{file_path}` без `/test`.

### REQ-TB-05 (M) Собственный HttpClient с настраиваемым таймаутом
Клиент должен передавать `HttpClient` параметром конструктора
`TelegramBotClient(options, httpClient)` (или `TelegramBotClient(token, httpClient)`):
именно так задаются кастомные заголовки (см. раздел 3) и таймаут.
`ITelegramBotClient.Timeout` проксирует `HttpClient.Timeout` — таймаут
настраивается через `HttpClient`, а не отдельной опцией.

**Приёмка:** переданный `HttpClient` используется всеми запросами пакета;
изменение `HttpClient.Timeout` меняет `botClient.Timeout`.

### REQ-TB-06 (M) Таймаут long-poll в диапазоне шлюза (0..60 с)
Шлюз поддерживает long-poll `timeout` 0..60. Пакет берёт таймаут поллинга из
`botClient.Timeout` (`request.Timeout = (int)botClient.Timeout.TotalSeconds`).
Клиент должен установить `HttpClient.Timeout` так, чтобы таймаут поллинга попадал
в 1..60 секунд (рекомендуется 25–30 с, типичное значение официального Bot API).

**Приёмка:** при конфигурации по умолчанию пакет шлёт `getUpdates` с
`timeout` ∈ [1..60]; при таймауте ≤ 60 шлюз не возвращает ошибку по параметру
`timeout`; long-poll не обрывается клиентом раньше сервера.

## 3. Заголовки apiId / apiHash

Контракт шлюза: для первого входа бота (создание auth_key и
`auth.importBotAuthorization`) нужны `X-Telegram-Api-Id` и `X-Telegram-Api-Hash`
(my.telegram.org). После сохранения сессии (`{botId}.bin`) заголовки не
обязательны, но безвредны — их можно слать на каждом запросе.

### REQ-TB-07 (M) Заголовки добавляются кастомным транспортом
В пакете **нет** встроенной опции «добавить заголовки» (токен уходит в путь URL,
а не в заголовок). Клиент должен обеспечивать наличие заголовков одним из двух
способов:
1. `DelegatingHandler` в составе передаваемого `HttpClient` (добавляет заголовки в
   `HttpRequestMessage` перед отправкой), **или**
2. событие `ITelegramBotClient.OnMakingApiRequest` — дополнение
   `e.HttpRequestMessage.Headers` / `e.HttpRequestMessage.Content.Headers`.

Заголовки должны присутствовать **на каждом** исходящем запросе (методы и
скачивание файлов): после первого логина они безвредны, а при потере сессии
позволяют переавторизоваться без вмешательства.

**Приёмка:** каждый запрос клиента к шлюзу содержит `X-Telegram-Api-Id` (числовой
api_id) и `X-Telegram-Api-Hash`; при выключенной/удалённой сессии первый же запрос
логинит бота без ручных действий.

### REQ-TB-08 (M) Заголовки не меняют URL и тело
Добавление заголовков не должно затрагивать путь запроса (`/bot{token}/{method}`)
и содержимое тела: токен остаётся в пути, JSON/multipart — как формирует пакет.

**Приёмка:** перехват исходящего запроса показывает неизменные URL и тело и
присутствующие оба заголовка.

### REQ-TB-09 (M) Обработка `401` как «требуется логин»
Если шлюз возвращает `error_code=401` (сессия отсутствует, api_id/api_hash
не приняты — например, неверная конфигурация), клиент должен обрабатывать
`ApiRequestException.ErrorCode == 401` как «нужен логин с api_id/api_hash»:
зафиксировать причину (лог), при восстановлении заголовков — продолжить работу,
не трактовать 401 как фатальный сбой бота.

**Приёмка:** при 401 клиент выдаёт понятную диагностику (какой бот, какой
api_id/hash-префикс) и не падает; после исправления конфигурации интеграция
работает без пересборки.

## 4. Транспорт, маршруты и формат запросов

### REQ-TB-10 (M) Маршруты — стандарт Bot API
Клиент (пакет) должен вызывать методы по шаблонам шлюза:

```
POST {base}/bot{token}/{method}            — методы (JSON или multipart)
GET  {base}/file/bot{token}/{file_path}    — скачивание файла
```

Пакет всегда использует POST для методов и GET только для скачивания — это
совместимо со шлюзом (который допускает и GET, и POST).

**Приёмка:** каждый вызов метода — POST `{base}/bot{token}/{method}`; скачивание —
GET `{base}/file/bot{token}/{file_path}`; иных путей клиент не генерирует.

### REQ-TB-11 (M) JSON-тело в snake_case с пропуском дефолтов
Клиент должен передавать аргументы в JSON по официальным именам Bot API
(`chat_id`, `text`, `message_id`, `caption`, `parse_mode`, …). Пакет делает это
сам: `PropertyNamingPolicy.SnakeCaseLower`, необязательные поля со значением по
умолчанию не сериализуются (`WhenWritingDefault`), обязательные — всегда.

**Приёмка:** тело запроса метода (например `sendMessage`) содержит
`{"chat_id": …, "text": …}`; нулевые/дефолтные опциональные параметры в тело не
попадают; шлюз принимает запрос без `400` по причине имени/типа параметра.

### REQ-TB-12 (M) Multipart для медиа с `attach://`
Для методов с файлами (`FileRequestBase`: `sendPhoto`, `sendDocument`,
`sendMediaGroup`, `sendRichMessage` с медиа и др.) пакет формирует
`multipart/form-data`: JSON-поля как `StringContent`, вложения — отдельными частями
с именами `"0"`, `"1"`, … и ссылками `attach://0`, `attach://1`, …
в JSON-поле. Клиент должен использовать именно этот механизм (через
`InputFile.FromStream`/`FromFileId`/…), не строя multipart вручную.

**Приёмка:** отправка медиа потоком уходит multipart с частями `name="0"…` и
`attach://N`; отправка по `file_id` — JSON-строкой; шлюз принимает оба варианта
без `400`.

## 5. Разбор ответов

### REQ-TB-13 (M) Единая обёртка `{ok, result}` и не-200 из тела
Клиент обязан разбирать ответ строго по обёртке Bot API:
- HTTP 200 → `{ "ok": true, "result": <тип> }` — возвращается `result`;
- HTTP ≠ 200 (например, `413`, `429` или `5xx`; и вообще любой не-200) → тело
  читается как
  `{ "ok": false, "error_code": <int>, "description": "<текст>", "parameters": … }`
  и превращается в `ApiRequestException(ErrorCode, Parameters)`.

Пакет делает это сам в `SendRequest`; клиентский код не должен полагаться только на
HTTP-статус — `error_code`/`description` берутся из тела.

**Приёмка:** при `413`/`429` и любом другом не-200 клиент получает
`ApiRequestException` с корректными `ErrorCode` и `Description` из тела; `result`
извлекается только при `ok=true`.

### REQ-TB-14 (M) Типизированные результаты
Клиент должен десериализовать `result` в типы официального Bot API через
типизированные запросы пакета: `User` (getMe), `Message` (sendMessage,
editMessage*), `Message[]` (sendMediaGroup), `Chat`/`ChatFullInfo` (getChat),
`ChatMember` (getChatMember), `int` (getChatMemberCount, getChatAdministrators —
массив `ChatMember[]`), `File`=`TGFile` (getFile), `bool` (`deleteMessage`,
`banChatMember`, `setChatTitle`…), `MessageId` (copyMessage).

**Приёмка:** все поддерживаемые методы (раздел 6) дают корректно типизированный
`result`; `copyMessage` читается как `MessageId` (`message_id`) — не полный
`Message`; bool-методы дают `true`.

## 6. Поддерживаемые методы: тиры 1–4, 501, webhook-400

### REQ-TB-15 (M) Работа строго в рамках тиров 1–4
Клиент должен использовать только методы, реализованные шлюзом:

- **Ядро:** `getMe`, `getUpdates`, `sendMessage`, `sendRichMessage` (см. раздел 12).
- **Тир 1 — медиа и файлы:** `sendPhoto`, `sendDocument`, `sendAudio`,
  `sendVideo`, `sendAnimation`, `sendVoice`, `sendVideoNote`, `sendSticker`,
  `sendMediaGroup`, `getFile` (плюс маршрут `/file/bot*`).
- **Тир 2 — правка и пересылка:** `editMessageText`, `editMessageCaption`,
  `editMessageMedia`, `deleteMessage`, `deleteMessages`, `forwardMessage`,
  `copyMessage`, `answerCallbackQuery`.
- **Тир 3 — чаты:** `getChat`, `getChatAdministrators`, `getChatMember`,
  `getChatMemberCount`, `setChatTitle`, `setChatDescription`, `setChatPhoto`,
  `leaveChat`, `banChatMember`.
- **Тир 4 — служебные:** `sendChatAction`, `setMyCommands`, `getMyCommands`,
  `answerInlineQuery`.

**Внимание:** пакет 22.10.4 содержит и другие методы Bot API 10.x (`SendWidget`,
`SendLivePhoto`, `SendChecklist`, ephemeral/подписочные и т.д.) — шлюз их **не**
реализует. Клиент не должен звать методы вне списка без готовности обработать
`501`.

**Приёмка:** в кодовой базе интеграции вызываются только методы перечня; вызовы
вне перечня (если есть) сопровождаются обработкой 501.

### REQ-TB-16 (M) Обработка `501` без зацикливания
Неизвестный/нереализованный метод возвращает
`{ok:false, error_code:501, description:"method '...' is not implemented"}`.
Клиент должен трактовать `ApiRequestException.ErrorCode == 501` как «шлюз не
поддерживает метод»: прервать вызов, залогировать, **не повторять** (в т.ч. не
давать встроенному retry пакета повторить — пакет и так ретраит только 429).

**Приёмка:** неподдерживаемый метод завершается управляемым исключением 501 без
зависания, зацикливания и повторов; приложение продолжает работу.

### REQ-TB-17 (M) Webhook-методы не используются; `400` обрабатывается
Шлюз long-poll only: `setWebhook`, `deleteWebhook`, `getWebhookInfo` отвечают
`400` `"webhooks are not supported; this gateway is long-poll only (use getUpdates)"`.
Клиент обязан не вызывать webhook-методы и не хостить приём webhook-а; получение
обновлений — только через `getUpdates` (раздел 7). Если webhook-метод всё же
вызван (ошибочная логика), `400` с этим описанием — штатная управляемая ошибка, а
не сбой.

**Приёмка:** в интеграции нет вызовов `setWebhook`/`deleteWebhook`/`getWebhookInfo`;
обновления доставляются через long polling; при случайном вызове клиент не падает.

### REQ-TB-18 (M) `copyMessage` возвращает `MessageId`
Ответ `copyMessage` — `{"message_id": N}` (не полный `Message`). Клиент должен
читать только `message_id`; остальные поля результата не требуются и могут
отсутствовать.

**Приёмка:** после `copyMessage` доступен `MessageId.Id`; код не обращается к
полям `Message` результата.

### REQ-TB-19 (S) `deleteMessages` — до 100 id
`deleteMessages` принимает `chat_id` + `message_ids` (1–100). Клиент должен
передавать не более 100 идентификаторов за вызов (лимит на стороне шлюза;
клиентской валидации в пакете нет) и подсказывать оператору при превышении.

**Приёмка:** пакетная отправка удалений не превышает 100 id за запрос; ответ
`true` трактуется как успех.

## 7. Обновления: long polling, allowed_updates, offset

### REQ-TB-20 (M) Получение обновлений — только long polling
Клиент должен использовать `StartReceiving`/`ReceiveAsync` (или ручной цикл
`GetUpdates`) — шлюз не поддерживает webhook. `update_id` назначает шлюз монотонно
на каждого бота; `offset` — подтверждение доставки (всё с `update_id < offset`
снимается с очереди).

**Приёмка:** обновления стабильно доставляются через `getUpdates`; после
перезапуска процесса клиента нумерация `update_id` продолжается (шлюз хранит
счётчик в сессии бота).

### REQ-TB-21 (M) Явный `allowed_updates` для callback/inline
Webhook-путь не используется, поэтому получение `callback_query` / `inline_query` /
`chosen_inline_result` зависит от списка `allowed_updates`, который шлёт клиент.

Особенность пакета: при отсутствии `ReceiverOptions.AllowedUpdates` поле
`allowed_updates` **не отправляется вовсе** (шлюз тогда отдаёт все типы, что тоже
приемлемо), а устаревший событийный API (`OnUpdate`/`OnMessage`) шлёт
`Update.AllTypes` (28 типов, включая не поддерживаемые шлюзом). Чтобы поведение
было детерминированным, клиент должен явно задавать:

```
AllowedUpdates = [ UpdateType.Message, UpdateType.CallbackQuery,
                   UpdateType.InlineQuery, UpdateType.ChosenInlineResult ]
```

(т.е. ровно те типы, что поддерживает шлюз) — не полагаясь на дефолт «все типы».

**Приёмка:** `callback_query` и `inline_query` приходят без дополнительных
настроек шлюза; `allowed_updates` в исходящем `getUpdates` соответствует списку
поддерживаемых типов.

### REQ-TB-22 (M) `offset` подтверждается штатно
При ручном режиме (`ReceiveAsync`/`GetUpdates`) клиент обязан передавать
`offset = последний обработанный update_id + 1` (при подтверждении) и не
забегать им вперёд без необходимости. При использовании `StartReceiving` пакет
управляет offset сам. Недоставленные апдейты остаются в очереди шлюза (до 10 000
на бота; при переполнении отбрасывается самый старый с предупреждением) — клиент
должен опрашивать достаточно часто, чтобы не терять апдейты.

**Приёмка:** каждый апдейт обрабатывается ровно один раз (или клиент явно
реализует идемпотентность); очередь шлюза не переполняется при штатной работе.

### REQ-TB-23 (M) `limit` и `timeout` в диапазонах шлюза
Клиент должен слать `limit` ∈ [1..100] и `timeout` ∈ [0..60] (см. REQ-TB-06 про
источник таймаута в пакете). Значения вне диапазонов шлюз не принимает.

**Приёмка:** исходящие `getUpdates` всегда содержат `limit` 1..100 и
`timeout` 0..60; шлюз не отвечает ошибкой по этим параметрам.

## 8. Резолв `chat_id`

### REQ-TB-24 (M) Все формы `chat_id` через тип пакета
Клиент должен передавать `chat_id` в формах, поддерживаемых шлюзом
(Integer | String):
- число: положительное — пользователь; отрицательное — базовый чат;
  `-100…` — канал/супергруппа;
- `@username` (или без `@`) — шлюз резолвит через `contacts.resolveUsername`
  (боты видят только публичные username);
- числовая строка (`"123456789"`) трактуется как число.

Пакет покрывает это типом `ChatId` с неявными преобразованиями из `long`,
`string` (`@username` или числовая строка), `Chat`, `ChatFullInfo`, `User` и
сериализацией «число → JSON-число, username → JSON-строка». Несуществующий
username → `400 Bad Request: chat not found` — должна быть обычная управляемая
ошибка (`ApiRequestException`), а не падение.

**Приёмка:** все перечисленные формы `chat_id` работают; `400 chat not found`
обрабатывается как штатная ошибка с понятным сообщением.

## 9. Текст: `entities` и `parse_mode`

### REQ-TB-25 (M) `entities` имеет приоритет над `parse_mode`
Если клиент передаёт `entities`/`caption_entities`, шлюз `parse_mode` не применяет
вовсе (текст уходит как есть). Клиент должен, задав `Entities`, не рассчитывать на
параллельный разбор `parse_mode` и, по возможности, не отправлять `parse_mode`
вместе с `entities` (чтобы поведение было однозначным).

**Приёмка:** сообщение с `Entities` доставляется как задумано без повторного
разбора; сообщение с `ParseMode` (без entities) форматируется шлюзом локально.

### REQ-TB-26 (M) Только поддерживаемые значения `parse_mode`
Шлюз разбирает локально только `HTML`, `Markdown` (legacy) и `MarkdownV2`;
неизвестное значение → `400 unknown parse_mode '...'`. Клиент должен использовать
только `ParseMode.Html`, `ParseMode.Markdown`, `ParseMode.MarkdownV2` из пакета и
не слать произвольные строки.

**Приёмка:** интеграция не получает `400 unknown parse_mode`; все три режима
работают.

### REQ-TB-27 (S) Смещения сущностей в UTF-16 не пересчитываются
MTProto и Bot API считают смещения в UTF-16 code units — шлюз передаёт их как
есть, не пересчитывая. Клиент должен передавать сущности с корректными
UTF-16-offset'ами (что пакет и делает: `MessageEntity` → snake_case JSON) и не
выполнять собственного пересчёта в code points.

**Приёмка:** сущности в текстах с юникодом (например, эмодзи перед форматируемым
фрагментом) применяются шлюзом точно.

## 10. Файлы: двухшаговое скачивание, коды ошибок, `file_id`

### REQ-TB-28 (M) Двухшаговое скачивание
Клиент должен скачивать файл строго в два шага:
1. `getFile(file_id)` → `TGFile` с `file_path`;
2. `DownloadFile(tgFile, destination)` (или `GetInfoAndDownloadFile`) →
   `GET {base}/file/bot{token}/{file_path}`, потоковое копирование.

Содержимое получается только через `/file/...`, а не из `getFile`.

**Приёмка:** байты файла получены по `file_path` из `getFile`; скачивание
потоковое (без загрузки всего тела в память сверх необходимости).

### REQ-TB-29 (M) `file_path` — непрозрачный маркер
`file_path` шлюза — неотгадываемый base64url-маркер in-memory кэша. Клиент должен
использовать его как есть, без декодирования, экранирования-изменения и
конструирования своих путей. Пакет вставляет `file_path` в URL без изменений.

**Приёмка:** скачивание проходит с оригинальной строкой `file_path`; изменённый
или «улучшенный» путь не используется.

### REQ-TB-30 (M) Ошибки скачивания обрабатываются
Клиент должен корректно обрабатывать при `getFile`/`DownloadFile`:
- `413` — файл больше `botApi.maxFileCacheBytes` (64 MiB) и не помещается в кэш
  шлюза;
- `502` с описанием про CDN (`CDN file download is not supported yet`) — CDN-файл
  шлюзом пока не поддерживается;
- `404` — `file_path` не найден (кэш вытеснен по LRU или перезапущен процесс).

Во всех случаях — понятное сообщение пользователю, без бесконечных повторов и
падения сессии.

**Приёмка:** все три кода завершаются управляемой ошибкой с внятным текстом;
клиент не ретраит `413`/`404` бесконечно.

### REQ-TB-31 (S) `file_reference` и истёкший `file_id`
`file_id` несёт снимок `file_reference`, который Telegram периодически ротирует.
При `getFile`/отправке с истёкшей ссылкой приходит ошибка `FILE_REFERENCE_EXPIRED`
(в `description`). Клиент должен в этом случае переполучить `file_id` из свежего
апдейта/повторной отправки, а не кэшировать ссылку навсегда.

**Приёмка:** после ротации `file_reference` клиент автоматически обновляет
`file_id` (или выводит понятное сообщение), а не шлёт мёртвый `file_id` вечно.

### REQ-TB-32 (S) `file_id` фото с типом размера
Массив `photo` в `Message` содержит **все доступные размеры** (`s`, `m`, `x`, …),
у каждого — свой `file_id`, `width`, `height`, `file_size`; `file_unique_id` общий.
`getFile` по такому `file_id` возвращает ровно запрошенный размер. Клиент может
выбирать размер по полям `PhotoSize`.

**Приёмка:** клиент умеет скачивать конкретный размер фото по его `file_id`, а
не только «самый крупный».

### REQ-TB-33 (M) Медиа — `file_id` или поток
Для отправки медиа клиент должен использовать `InputFile`:
- `InputFile.FromFileId(id)` / `FromString(urlOrFileId)` — повторное
  использование ранее полученного `file_id` (или URL);
- `InputFile.FromStream(stream, fileName)` — новая загрузка (multipart,
  `attach://`, см. REQ-TB-12);
- локальные `file://` URI — только при явном
  `InputFileConverter.AllowLocalFilesUnder`, иначе пакет вернёт
  `400 "file:// URI not allowed"`.

**Приёмка:** новая загрузка потоком и повторная отправка по `file_id` дают
корректные ответы без `400`.

## 11. Лимиты и отказоустойчивость

### REQ-TB-34 (M) `429` с `retry_after` уважается
Шлюз отдаёт `429` с `parameters.retry_after` (свой rate-limit
`requestsPerSecondPerToken`, по умолчанию 30 запросов/с на бота, и флуд-лимиты
Telegram `FLOOD_WAIT_X`; дополнительно заголовок `Retry-After`). Клиент обязан
следовать `retry_after`, а не ретраить мгновенно.

Пакет уже делает правильно: встроенный retry **только** для `ErrorCode == 429`
и `retry_after ≤ RetryThreshold` (по умолчанию 60 с), до `RetryCount` (по
умолчанию 3) попыток с паузой `retry_after` секунд. Клиент должен:
- не менять `RetryThreshold`/`RetryCount` на агрессивные значения;
- при `retry_after > 60` или исчерпании попыток — собственная пауза и повтор не
  ранее указанного времени (либо управляемая ошибка);
- помнить, что другие статусы (`413`, 5xx) пакет не ретраит.

**Приёмка:** при 429 запрос повторяется не мгновенно, а с паузой `retry_after`;
после паузы запрос проходит; при `retry_after > 60` клиент не зацикливается.

### REQ-TB-35 (M) Лимит загрузки (`maxUploadBytes`, 20 MiB)
Клиент должен учитывать `botApi.maxUploadBytes` (по умолчанию 20 MiB суммарно на
multipart-вложения): по возможности проверять размер до отправки; при `413` —
сообщать об ошибке, **не повторять** запрос бесконечно.

**Приёмка:** загрузка сверх лимита завершается штатной ошибкой `413` с понятным
сообщением (какой файл, какой лимит), без зависания и бесконечных ретраев.

### REQ-TB-36 (S) Транспортные `502` — ограниченный повтор
Шлюз может отдавать `502` при временных сбоях (переподключение к Telegram,
CDN-ошибка). Клиент должен отличать `502` от ошибок метода и применять
**ограниченный** повтор (пакет сам 5xx не ретраит) с экспоненциальным backoff и
потолком попыток, не роняя сессию. `502` с текстом про CDN повторять бессмысленно
(REQ-TB-30).

**Приёмка:** временный `502` не роняет сессию клиента; количество повторов
ограничено.

### REQ-TB-37 (S) Прочие не-200 не ретраятся без причины
Клиент не должен ретраить 4xx кроме `429` (и, при необходимости, обработки
`401` как «требуется логин» — см. REQ-TB-09): `400`, `404`, `413`, `501`
означают ошибку запроса, а не временный сбой.

**Приёмка:** в коде интеграции нет общих retry-обёрток поверх всех ошибок;
каждый код обрабатывается по смыслу.

### REQ-TB-38 (S) Миграция группы в супергруппу — без `migrate_to_chat_id`
Шлюз **не** отдаёт `parameters.migrate_to_chat_id` (в отличие от официального Bot
API поле у пакета `ResponseParameters.MigrateToChatId` останется `null`). Клиент не
должен полагаться на авто-миграцию: при ошибке после превращения группы в
супергруппу (`400 … group chat was upgraded to a supergroup chat`) следует
получить новый `chat_id` (из свежего апдейта, конфигурации или иным способом)
и повторить вызов с ним.

**Приёмка:** сценарий «группа → супергруппа» не роняет клиента и не приводит к
попытке читать отсутствующий `migrate_to_chat_id`; клиент обрабатывает
`MigrateToChatId == null` штатно.

## 12. `sendRichMessage` (Bot API 10.1)

### REQ-TB-39 (M) Штатный метод пакета
Начиная с версии, покрывающей Bot API 10.1 (в 22.10.4 — точно), `sendRichMessage`
**уже реализован в пакете**: расширения `ITelegramBotClient.SendRichMessage(...)`
и `SendRichMessageDraft(...)` + тип `InputRichMessage`
(`Html` | `Markdown` | `Blocks`, `IsRtl`, `Media`, `SkipEntityDetection` —
ровно одно из `Html`/`Markdown`/`Blocks`). Клиент должен использовать штатный
метод, а не ручной HTTP.

Контракт шлюза: `rich_message` с `html` **или** `markdown` (+ опц. `rtl`,
`disable_autolink`) уходит через `messages.sendMessage` с флагом rich_message.
Особенности:
- у rich-сообщения нет текстового тела — в ответе `text` пустой; контент читается
  из `rich_message` в самом сообщении (в пакете — `Message.RichMessage`,
  `MessageType.RichMessage`);
- поле `rtl` соответствует `InputRichMessage.IsRtl`;
- `disable_autolink` в типе пакета нет — при необходимости его передать
  требуется кастомный запрос (REQ-TB-40).

**Приёмка:** `SendRichMessage` с `Html`/`Markdown` (+ `IsRtl`) принимается шлюзом
и доставляется; ответный `Message` имеет пустой `text` и заполненный
`RichMessage`/`MessageType.RichMessage`.

### REQ-TB-40 (O) Кастомные запросы для отсутствующих методов
Если понадобится метод, которого в текущей версии пакета нет (например,
дополнительные параметры `rich_message` вроде `disable_autolink`, или новый метод
более свежего Bot API), клиент должен реализовать его через
`IRequest<TResponse>` (наследование `RequestBase<TResponse>` /
`FileRequestBase<TResponse>` для multipart) и вызвать
`await botClient.SendRequest(request, ct)`. Кастомный запрос автоматически получает
те же заголовки (REQ-TB-07) и ту же обработку ошибок, что и штатные.

**Приёмка:** метод вне обёртки пакета вызывается с теми же заголовками и
разбором `{ok,result}`; шлюз принимает запрос по шаблону
`POST {base}/bot{token}/{method}`.

## 13. Фиксированный набор полей ответов (не полагаться на отсутствующее)

### REQ-TB-41 (M) `Message` — только поля, которые шлюз умеет собрать
Шлюз собирает объект `Message` из фиксированного набора полей:
`message_id`, `date`, `text`/`caption`, `from`, `chat`, `entities`/`caption_entities`,
`photo`, `document`, `reply_to_message`, `quote`, `message_thread_id`,
`is_topic_message`, `forward_origin`, `edit_date`, `views`.
Новые опциональные поля апстрима в ответах **не появляются** (например, полей
`sticker`/`video`/`voice`/`audio`/`animation`/`video_note` в составе медиа-сообщений
может не быть). Клиент обязан трактовать отсутствующее поле как отсутствующее
(null/0/false), а не как ошибку — пакет это поддерживает (все поля `Message`,
кроме обязательного `Id`, nullable). Не полагаться на не входящие в список поля и
не требовать их для логики.

То же относится к версии API: шлюз **не объявляет** `api_version` ни в ответах,
ни в `getMe` — клиент не должен требовать/проверять это поле.

**Приёмка:** бот корректно работает с сообщениями, где часть опциональных полей
`Message` отсутствует (в т.ч. медиа-сообщения без ожидаемых медиа-полей кроме
`photo`/`document`); отсутствие поля не вызывает исключений и не ломает логику;
код не проверяет `api_version`.

### REQ-TB-42 (M) Ограниченный `reply_to_message` и параметры reply
Шлюз не дозапрашивает тело цитируемого сообщения: `reply_to_message` в ответах
может содержать только то, что собрано локально (без полного тела цитаты). При
отправке reply-параметры принимаются из `reply_to_message_id`, `message_thread_id`
и объекта `reply_parameters` (`message_id`, `quote`, `quote_entities`,
`quote_position`); `allow_sending_without_reply` игнорируется. Клиент должен
использовать штатные поля пакета (`ReplyToMessageId`, `MessageThreadId`,
`ReplyParameters`) и не требовать полного тела цитаты в ответе.

**Приёмка:** отправка reply по `reply_parameters`/`reply_to_message_id` работает;
чтение ответного `reply_to_message` не требует отсутствующих полей; поведение не
зависит от `allow_sending_without_reply`.

### REQ-TB-43 (S) `getChat` — только отдаваемые поля
`getChat` возвращает базовые поля (`id`, `type`, `title`, `username`) плюс из
full-info: `description`, `invite_link`, `permissions`, а для каналов — `is_forum`,
`has_protected_content`, `has_hidden_members`, `has_aggressive_anti_spam_enabled`,
`slow_mode_delay`, `linked_chat_id`. Намеренно **не** отдаются: `photo`, `pinned_message`,
`has_visible_history`. Клиент не должен обращаться к этим трём полям как к
гарантированным (отсутствие → null, как в REQ-TB-41).

**Приёмка:** код интеграции не использует `photo`/`pinned_message`/
`has_visible_history` из результата `getChat` как обязательные.

## 14. Безопасность и логирование

### REQ-TB-44 (M) Токен не логируется открыто
Токен передаётся в пути URL (`/bot{token}/…`) — это дизайн Bot API, изменить
нельзя. Клиент обязан при логировании исключений, URL и диагностики маскировать
токен в формате шлюза (`botId:***`): не писать полный токен и полный `apiHash` в
логи (шлюз сам маскирует секреты, в т.ч. `apiHash` — видны только последние 4
символа). Не ожидать полного `api_hash`/токена в ответах и диагностике шлюза.

**Приёмка:** в логах клиента (включая тексты исключений с URL) нет полного токена;
секреты не выводятся в открытом виде.
